# Архитектура

## Обзор

```text
GNOME panel menu
      │
      │ Gio.Subprocess (async)
      ▼
~/.local/bin/g6-output
      │
      │ hidapi / hidraw
      ▼
Sound BlasterX G6 control interface

Локальный кеш:
${XDG_STATE_HOME:-~/.local/state}/g6-output/output
```

Проект использует модель «CLI как граница системы». GNOME extension ничего не
знает о USB-протоколе: он вызывает бинарник и реагирует на exit code/stdout.

## Компоненты

### `src/main.rs`

Единый Rust-бинарник отвечает за:

- разбор CLI-команд;
- поиск конкретного HID-интерфейса;
- формирование и отправку output command;
- локальный кеш;
- базовую диагностику;
- unit-тесты протокольного пакета.

Для MVP код оставлен в одном файле. После подтверждения протокола разумно
разделить его на `cli`, `device`, `protocol`, `state` и `error`.

### `extension/extension.js`

Тонкий UI-адаптер GNOME Shell:

- создаёт panel indicator: левый клик — `toggle`, правый — меню. На GNOME 50
  это делается двумя `Clutter.ClickGesture` с разным `required_button`, потому
  что `PanelMenu.Button` там перехватывает нажатие жестом, а не `vfunc_event`;
  для GNOME 48–49 оставлена ветка на `vfunc_event`;
- скрывает индикатор при `disconnected` и показывает при подключении;
- следит за hidraw через `GUdev.Client`; события отфильтрованы по
  `ID_VENDOR_ID`, склеены debounce 300 мс, а подключение получает две
  дополнительные попытки, потому что перечисление отстаёт от uevent;
- запускает `~/.local/bin/g6-output` через `Gio.Subprocess`;
- не блокирует main loop;
- обновляет UI только после exit code `0`;
- показывает системные уведомления.

Extension не читает `hidraw`, не хранит собственный persistent state и не
использует root.

### `packaging/70-soundblaster-g6-output.rules`

Правило:

```udev
SUBSYSTEM=="hidraw", ATTRS{idVendor}=="041e", ATTRS{idProduct}=="3256", TAG+="uaccess"
```

Оно передаёт доступ активному локальному пользователю через systemd-logind.
Правило не ограничивает interface `4`; правильный интерфейс дополнительно
выбирает приложение. Это нужно проверить с точки зрения минимальных прав и при
необходимости сузить правило по доступным udev attributes.

### `install.sh` и `uninstall.sh`

Пользовательские файлы ставятся в `$HOME`, а `sudo` применяется только к
`/etc/udev/rules.d/70-soundblaster-g6-output.rules` и `udevadm`.

Установщик умеет взять бинарник из:

1. `bin/g6-output` в release archive;
2. `target/release/g6-output` локальной сборки;
3. собрать его через Cargo.

### `scripts/package.sh`

Создаёт:

- полный installable tarball;
- отдельный zip GNOME extension;
- `SHA256SUMS`.

### `.github/workflows/release.yml`

Один build job выполняет проверки и упаковку. Отдельный release job запускается
только для `refs/tags/v*` и публикует ранее созданные артефакты.

## HID-протокол

Протокол подтверждён на реальном устройстве 29 июля 2026 года
(Bluefin 44, GNOME 50.3, kernel 7.0.12, firmware не опрашивалась).

### Транспорт

Control interface `4` соответствует `/dev/hidraw7` на тестовой машине. Его
report descriptor:

```text
06 00 ff 09 01 a1 01 19 01 29 40 15 00 26 ff 00
75 08 95 40 81 00 19 01 29 40 91 00 c0
```

То есть Vendor-Defined Page `0xFF00`, Report Size 8 бит × Report Count `0x40`,
Input и Output по 64 байта, **Report ID отсутствует**. По соглашению hidapi при
отсутствии Report ID запись выполняется 65 байтами с ведущим `0x00`, а чтение
возвращает 64 байта уже без него. Отсюда `REPORT_SIZE = 65` и `PAYLOAD_SIZE = 64`.

Наличие Input report — причина, по которой чтение состояния и ACK вообще
возможны.

### Формат кадра

| Offset (payload) | Значение | Назначение |
|---:|---:|---|
| `0` | `0x5a` | начало payload |
| `1` | `0x2c` | команда выбора выхода |
| `2` | `0x05` | длина команды |
| `3` | `0x00` / `0x01` | селектор: `0x00` — запись, `0x01` — чтение |
| `4` | `0x02` / `0x04` | динамики или наушники |
| `5..63` | `0x00` | padding |

Соответствие подтверждено на слух: `0x04` — наушники, `0x02` — динамики.

### Чтение состояния

Запрос `5a 2c 05 01 00` возвращает `5a 2c 05 01 <mode>` с фактическим текущим
выходом. Именно на этом построены `status`, `toggle` и `doctor`.

### Подтверждение записи

Ответом на запись `5a 2c 05 00 <mode>` устройство присылает кадр в той же
read-форме `5a 2c 05 01 <mode>`, где `<mode>` — реально применённое значение.
Поэтому `set` сравнивает запрошенный режим с подтверждённым и возвращает
ошибку `NotApplied` при расхождении, а не полагается на код возврата
системного вызова.

### Асинхронные события

Устройство также присылает незапрошенные кадры с другим номером команды —
например `5a 6e 02 01 00` после смены выхода. Они приходят вперемешку с
ответами, поэтому `read_output_reply` **обязан** фильтровать по байту команды
`0x2c`, а не брать первый пришедший report. Неверные команды получают
error-ответ вида `5a 02 0a 2c 80`.

Эти event-кадры — готовая основа для будущего hot-plug/watch-режима, но в MVP
они игнорируются.

## Потоки выполнения

### Явное переключение

1. Пользователь выбирает пункт GNOME или вызывает CLI.
2. CLI создаёт `HidApi`.
3. Ищет VID/PID/interface.
4. Открывает устройство.
5. Отправляет report.
6. Читает ответ устройства и сверяет применённый режим с запрошенным.
7. Только после подтверждения сохраняет локальный кеш.
8. Печатает выбранный output и завершается с кодом `0`.
9. Extension обновляет иконку и уведомляет пользователя.

### `toggle`

`toggle` читает фактический выход из устройства и переключает на
противоположный. Если устройство не отвечает, команда завершается ошибкой — она
не угадывает состояние.

### `status`

`status` опрашивает устройство и печатает `headphones`, `speakers`,
`disconnected` (устройство не найдено) либо `unknown` (устройство есть, но
ответ получить не удалось, и кеш пуст). Команда намеренно не завершается
ошибкой: индикатор GNOME вызывает её при старте и ему нужно слово, а не exit
code. Локальный файл остался резервом на случай отсоединённого устройства.

### `doctor`

`doctor` проверяет наличие нужного HID interface, открывает его и выполняет
read-запрос, то есть подтверждает и доступ, и работоспособность протокола. Он
печатает фактический выход и кешированное значение рядом, чтобы расхождение
было видно. Если interface `4` не найден, но устройство присутствует, `doctor`
перечисляет остальные найденные интерфейсы.

## Ключевые решения

### Почему без демона

Для двух редких переключений постоянный процесс, D-Bus API и lifecycle management
увеличили бы сложность без существенной пользы. CLI проще устанавливать,
диагностировать и удалять.

Демон станет оправданным при hot-plug monitoring, чтении состояния, профилях или
частых двусторонних событиях.

### Почему GJS остаётся

GNOME Shell extensions работают в GJS. Rust используется для всего
низкоуровневого кода, но нативный Rust не заменяет extension entrypoint.

### Почему не PipeWire

Проект управляет физическим режимом G6, а не выбирает software sink. PipeWire и
GNOME sound settings решают соседнюю, но не идентичную задачу.

## Основные риски

- protocol подтверждён на одном экземпляре G6; другие firmware не проверялись;
- interface number может отличаться в отдельных конфигурациях (`doctor` теперь
  показывает найденные альтернативы);
- GNOME API может измениться между заявленными версиями; реально проверена
  только 50.3;
- udev-rule может оказаться слишком широким или не сработать в конкретной
  immutable-дистрибуции;
- отсутствует hot-plug: состояние обновляется при открытии меню;
- ACK читается с общим лимитом 1 с; на медленной шине это может оказаться мало.
